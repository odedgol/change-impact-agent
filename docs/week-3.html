Week 3: approval and a reversible executor

The report becomes an action, but only through code-checked guardrails, a person's approval and an executor that disables first and can undo every step.

Status
active · plan approved with the recommended answers; PR 3.1–3.5 merged, PR 3.6 in review · updated 2026-10-18
Delivers
ChangeWorkflow: investigate → guard → approve → act
Done when
make bench-fake prints unsafe_deletes: 0 and unapproved_actions: 0

Week 2 answers "is it safe?". Week 3 does something with the answer. A second LangGraph graph wraps the investigator. Plain functions decide which actions the verdict allows. interrupt() waits for a person. The executor then dry-runs, disables, waits a quiet period, checks again, and deletes or restores. Every step is written to an append-only audit log.

Where this sits: the request loop, steps 5 and 6, and the dashed week-3 boxes in the five layers.

What each verdict may do

VerdictAllowed actionsAfter the quiet period
safe_to_deletedisable, then deletedelete if nothing used it; else restore
disable_firstdisable onlyrestore if used; else stays disabled, and a new run is needed before any delete
ask_ownernonestop; the owner is asked
insufficient_evidencenonestop; run again when the source is back

A person can approve less than the guardrails allow, never more. Protected identities (break-glass, the tenant's own admins) allow no action, whatever the verdict.

Open questions

All answered on 2026-10-17: the recommended answer was taken for each.

Q10decided

How do we model credential chains?

userownsAPI keystored insecretread bypipelineowned byteam

Decided (recommended): one new credential_chain command, added at the end of COMMANDS (the golden org hash changes on purpose). Four dependency kinds: owns_credential, stored_in, read_by, owned_by. get_dependencies(identity_id, depth=1) follows up to 4 hops; each row carries hop and via, and code clamps depth to 1–4. Expected verdict: ask_owner.

Q12decided

Can a person approve more than the guardrails allow, for example a delete on ask_owner?

Decided (recommended): no. A person can only narrow. To widen, record the owner's answer as a ticket and run the investigation again, so the reason is evidence.

Q13decided

Which checkpointer holds the two waits?

Decided (recommended): SqliteSaver (langgraph-checkpoint-sqlite) in data/ now, with the same allow-listed serializer as week 2. Postgres later, behind the same LangGraph interface. A wait must survive a restart.

Q14decided

How long is the quiet period, and what ends it early?

Decided (recommended): 14 days, set in config. Any sign-in or key use while disabled ends it with a restore. A scheduler, or make resume in the demo, resumes the graph with the current time; tests use a fake clock.

Q15decided

How old can a report be at approval time?

24 hours. Revised in PR 3.4b: what decides is whether the evidence changed, not its age. A snapshot fingerprints fresh reads of the five tools before each investigation. When the person answers, they are read again. Unchanged: the same report stands, with no model call. Changed: investigate again and ask again. Unreadable: stop. A 7-day age limit stays as a backstop. No cache: every check reads fresh, so there is one source of truth.

Q16decided

What makes the audit log trustworthy?

Decided (recommended): JSON lines; each entry holds the hash of the one before. verify() finds any edit or gap. Each action has an idempotency key (request_id + action), so a retry or resume never acts twice.

Validation

Each item is a test or a command. CI runs make lint typecheck test, make bench-fake and the tui job on every PR.

  • test_generator_golden.py: the new org hash is pinned, and the PR says why it changed. The credential_chain case is found only by following hops; the naive baseline deletes it. PR 3.1: 24 cases, the naive rule deletes 8 of 12 risky accounts, 148 tests.
  • test_guardrails.py: every row of the verdict table; a protected identity allows nothing; a 25-hour-old report allows nothing; an approval that asks for more than allowed is refused. PR 3.2: 19 tests, 167 in total.
  • test_executor.py: a dry run changes nothing; disable then restore gives back the same row; running the same action twice acts once; delete without a prior disable is refused; the evidence database is unchanged after every test. PR 3.3: 14 tests.
  • test_audit.py: every action writes one entry; editing, removing or reordering an entry makes verify() fail. PR 3.3: 5 tests, 186 in total.
  • test_workflow.py, on the rule model and a fake clock (11 tests, 197 in total):
    • the run stops at approve, and nothing has changed on the target;
    • decline ends with no change; approve runs dry run → disable → quiet;
    • use during the quiet period restores; no use deletes, only for safe_to_delete;
    • a restart between the waits resumes from the checkpoint and never acts twice.
  • test_investigator.py: a safe_to_delete on a nightly job, an owned account, a break-glass account or a credential chain, citing real ids, becomes ask_owner; one that cites only usage too. test_workflow.py: unchanged evidence keeps the report without a model call; a new ticket before approval investigates again; a failed read stops; a change during the quiet period restores; approval after 7 days acts on nothing. PR 3.4b: 211 tests.
  • test_monitor.py: start → approve → end quiet period → deleted through HTTP; approving before start, starting twice and resuming while waiting for a person are refused (409); an empty name, an unknown action or no action is refused (400); a text/plain POST or one from another Origin is refused (403). test_workflow.py: the command line runs a change end to end into one trace. Rust: the smoke replay has 11 runs, outcomes deleted and declined, and a re-investigation in one run. PR 3.5: 217 tests + 11 Rust.
  • make bench-fake prints unsafe_deletes: 0, unapproved_actions: 0 and wrong_deletes: 0. PR 3.6; the gate test with grounding off now also counts 12 wrong deletes.
  • test_graph.py: the hub's drawing matches both graphs. PR 3.6: 220 tests.

Rollout and rollback

PRs merge in order 3.0 → 3.6, each small and additive. The investigator and its events don't change, so week-2 tools (bench, monitor, Rust UI) keep working at every step. Revert a squash commit to roll it back. Only synthetic data; nothing is deployed and no real system is touched.
