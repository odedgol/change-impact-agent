Change Impact Agent

Before an identity or permission is deleted or changed, an agent gathers evidence and returns a risk report with confidence and a safe recommendation. A separate reversible executor runs only after human approval. Status: week 1 done, week 2 next.

PRD

Problem. Deleting an "unused" identity breaks hidden dependencies: nightly jobs, policy exceptions, shared and break-glass accounts. A naive "no usage in 90 days" rule breaks 6 of the 10 risky accounts in our benchmark.

Goal. For each change request, return safe_to_delete, disable_first or ask_owner, with every finding citing evidence ids. Never recommend an unsafe delete.

#Requirement
FR1Accept a change request (identity id, action).
FR2Investigate using read-only evidence tools: usage, dependencies, tickets, owner.
FR3Return a structured RiskReport; each finding cites evidence ids and has a confidence.
FR4Guardrails in code decide what may proceed; the prompt is not a control.
FR5Wait for human approval (Temporal signal) before any action.
FR6Executor: dry-run, disable first, undo, idempotent.
FR7Append-only audit log.
FR8Benchmark harness: recall, precision, calibration, stability, cost.

Not building: a UI product, a real IdP integration at the start, auto-approval, multi-tenant auth.

Proposed targets, not proven: recall on planted dependencies ≥ 90%, precision on alarms ≥ 80%. Hard gate: 0 unsafe-delete recommendations.

Design

Solid arrows call; dashed arrows implement. The investigator knows only the two interfaces, so every outside system is swappable.

Test layers: unit (tools, guardrails) → interface contract tests on fake and real implementations → workflow tests with time-skipping → full benchmark with the real model → red-team and chaos cases.

Field proof without a real org: run against a personal AWS account (IAM roles, CloudTrail, last-accessed data) and compare to what you know. Small, but it shows the agent is not built only for the synthetic org.

Fix loop: classify each failure (missing tool, bad recommendation, no evidence, wrong citation), fix in that order (tool, then prompt, then code rule), and record every run in a results table (version, recall, precision, change). That table is the best thing to post.
