Investigator loop and RiskReport

Week 1 shipped the synthetic org, read-only tools and a naive baseline that breaks 6 of 10 risky cases. Week 2 adds the agent: two swappable interfaces, a tool-calling loop, and a structured report where every finding cites evidence ids that code verifies.

Goal

investigate(request) -> RiskReport runs a tool-calling loop over an LLMClient and returns one verdict with a confidence:

safe_to_deletedisable_firstask_owner

Every finding cites evidence ids that exist in that run's tool log, such as ev-deps-3. Proven end-to-end with FakeLLM, plus one smoke run on Bedrock.

System topology

The five layers of an agentic system, mapped onto what this project builds. Solid = week 2. Dashed = week 3+, asynchronous or proposed. Edge labels are the payload that moves along that edge.

One LLM worker, not a team. The supervisor and router are plain code, so the step order can't be talked out of. Evidence ids are assigned by code, never by the model, and the critic is a code check, so a report can only cite what a tool actually returned in this run.

Open Questions

Four questions are open. Each has a recommended answer; reply with the number and "yes" or your change.

Q8openweek 2

Should the critic force a retry when citations are rejected?

RecommendedYes, at most 1 retry. Send rejected_ids back to the model; the retry counts against the 8-call cap. If it fails again, Q7 applies. Adds one investigator test.

Q9openweek 4

Keep an index of internal docs (runbooks, wikis, READMEs, Slack) for evidence that never names the account id?

RecommendedYes, as a measured week-4 experiment.
  • Hybrid search: keyword for exact names (prod/flow/es, etl-writer) plus embeddings for paraphrases, on pgvector inside Postgres.
  • Index when a doc changes, never per investigation.
  • At index time, extract candidate links from docs ("Flow gets its ES key from Vault, owner Dana"), each pointing back to its source doc.
  • An alias table maps names, emails and handles to identity_id.
  • Docs are leads, not proof. A doc-only finding caps the verdict at ask_owner. High confidence needs confirmation from an authoritative system.
  • Measure with a new case type, doc_only_dependency: run the baseline without the index first, then with it.
Q10openweek 3

Model credential chains, such as a leaver's Elasticsearch API key that a pipeline still uses?

user→ owns →ES API key→ stored in →secret→ read by →pipeline→ owned by →team

RecommendedYes, in week 3 before the guardrails.
  • New case type credential_chain in the generator.
  • New dependency kinds: owns_credential, stored_in, reads_secret, owned_by_team.
  • get_dependencies follows links up to 4 hops and logs each hop as its own evidence item.
  • Each link comes from the system that knows it: the ES API (key owner), Vault or Secrets Manager (where it's stored), access logs (who reads it), the service catalog (owning team). Real connectors stay optional.
Q11openweek 4

Should doc search widen its terms from what each round finds?

RecommendedYes, together with Q9.
  • search_docs(terms, filters, from_evidence). Every term must come from cited evidence, so the model can't invent search terms and a doc can't steer the search.
  • Rank by how many known chain items appear together. Filter by environment, service and doc age, so broad words like "prod" don't flood the results.
  • At most 4 rounds; stop when a round adds nothing. Rounds count toward the tool-call cap, which rises from 8 to 12 in week 4.
  • Each search is logged as evidence (ev-search-2), so the report shows why a doc was found.
