Process · Git flow

How a change gets into main

Every pull request is tested and reviewed before it merges into main. Every PR also says what changed in plain words and links the docs page that explains it.

01 · Rules

Three things before any merge

Tested

The tests pass on Python 3.12 and 3.13. If the agent logic changed, the bench still shows 0 unsafe deletes.

checked by: CI job test
Reviewed

The code has been reviewed and every review comment is resolved.

checked by: branch protection
Explained

The PR says what changed in 1–3 bullets and links the docs/*.html page that explains it, including any design change.

checked by: CI job pr-description

Nobody can push straight to main, and you can't force-push to it. Every change goes through a PR.

02 · Flow

From branch to main

  1. PlanWrite or update docs/week-N.html before writing code.
  2. BranchStart a short-lived branch off main, one slice per branch.
  3. Open PROpen it as a draft and fill in the template.
  4. CI checksTests and the description check run on every push.
  5. ReviewRun a code review and resolve every comment.
  6. MergeSquash-merge into main, then delete the branch.
  7. Close the loopTick the checks in the docs page and mark the step done.
If a gate failsPush a fix to the same branch. CI runs again and the PR stays open. Don't open a new PR.

03 · PR description

What a reviewer reads first

GitHub fills in this template when you open a PR. Write it so someone who hasn't seen the code understands it in 30 seconds.

SectionWriteRequired
## What changed1–3 plain bullets: what the code or docs can do now that they couldn't before.CI
## DocsA link to the docs/*.html page and section. Say whether the design changed and, if it did, what moved.CI
## How to testThe exact commands to run and what the reviewer should see.CI
## Review checklistTick each box once it's true.yes
## Out of scopeWhat this PR deliberately leaves out, and which PR will do it.optional

Example

## What changed
- Adds Pydantic models: ChangeRequest, Evidence, Finding, RiskReport.
- A Finding with no evidence ids is now rejected at parse time.

## Docs
- Plan / spec: docs/week-2.html#steps (step 2)
- Design changed? no

## How to test
make test   # 7 week-1 tests + 4 new model tests pass

05 · Review

Who reviews

Now (one author)When a teammate joins
Run Claude Code /code-review --comment on the PR. It posts findings as inline comments. Fix each one or reply, then resolve it. The author goes through the review checklist. Raise branch protection to 1 required approval. The rest stays the same.

GitHub doesn't let you approve your own PR, so for now "reviewed" means: the review has run, and branch protection blocks the merge until every review comment is resolved.

07 · Cheat sheet

One PR, start to finish

  1. 1. Start a slice from an up-to-date main
    git switch main && git pull && git switch -c w2/tooling-models
  2. 2. Check it locally before pushing
    make test
  3. 3. Open a draft PR (the template fills in the description)
    git push -u origin HEAD && gh pr create --draft --fill-first
  4. 4. Watch the checks, then review
    gh pr checks --watch
/code-review --comment     # in Claude Code
  5. 5. Merge when green and all comments are resolved
    gh pr ready && gh pr merge --squash --delete-branch
