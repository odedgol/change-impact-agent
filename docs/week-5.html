Week 5: the real demo

Talk to the bot in Slack in your own words, and let it answer from real systems: a real identity provider, a real AWS account with real keys and a real job, real tickets.

Status
active · plan approved (2026-10-18), Q25–Q28 with the recommended answers; PR 5.0 merged, PR 5.1 in review · updated 2026-10-18
Delivers
A chat bot with read-only tools; Keycloak, AWS and GitHub adapters; one end-to-end demo on them
Done when
The recorded demo runs on real systems, every gate is 0, and make aws-check prints 0 afterwards

Week 4 ended with a Slack demo on a mocked org: the bot matched names in code and showed cards. That proves the flow, not real life. In real life an IT or security person asks "who left this week?", "can I delete Noah yet?", "anything blocking?", and the answers come from the systems the company runs. Week 5 builds exactly that. What does not change: the investigator, the change workflow, the guardrails, the executor, the audit log and the bench gates. Approval stays on the Slack buttons, for allow-listed approvers only.

The people are invented, even inside the real systems, so a hosted chat model (OpenRouter Gemma 4) is fine. With real employee data the chat would move to Bedrock in the company's own account; the code takes either through LLMClient.

The demo

HR marks Noah Novak as gone in Keycloak. Nobody presses Start.

HR Keycloak: Noah Novak · hr_status=left · last_day=today

agent reads Keycloak logins, CloudTrail use of his AWS key, the Lambda that holds it, the GitHub issues; posts a card in #it-offboarding: disable_first · [Approve disable] [Decline]

you @agent who left this week?

bot Three people: Noah Novak (legal; his key was used 2 hours ago by a Lambda), Wei Lee (finance; owns an API key used by a log pipeline), Noah Smith (data; nothing found).

you can I delete Noah yet?

bot No. The nightly-report Lambda used his access key AKIA…3GXC at 02:00 today (CloudTrail), and the secret prod/nightly-report holds it.Guardrails: allowed = disable only. Approve on the change message.

you [Approve disable] → the key goes Inactive in AWS, the Keycloak user is disabled

bot Next night: the Lambda failed with InvalidClientTokenId. Use seen during the quiet period → restore offered.

The guardrail line is added by code under the model's answer. The model cannot change it, and it cannot approve, disable or delete anything: it only has read-only tools.

Open questions

All answered on 2026-10-18: the recommended answer was taken for each.

Q25decided

How long does the bot remember a Slack thread?

Decided (recommended): 7 days, per thread, in the local checkpointer; then it starts fresh. Nothing from a thread ever reaches the investigator.

Q26decided

Can someone ask the bot to investigate a person HR has not reported yet?

Decided (recommended): yes, but not by the model. The answer shows a "Start investigation" button; only approvers can click it, and it sends the same signed HR event. The chat itself stays read-only.

Q27decided

What do disable and delete do in AWS and Keycloak?

Decided (recommended): disable = access keys Inactive and a deny-all cia-quarantine policy attached in AWS, user enabled=false in Keycloak (all undone by restore). Delete, only after the quiet period: keys deleted, policies detached, IAM user deleted, Keycloak user deleted.

Q28decided

How many people go into the real systems?

Decided (recommended): Keycloak gets the demo org's 103 people (free and local). AWS gets 8 IAM users: the traps that need the cloud (the nightly job, the credential chain, the break-glass account, a lookalike) and four plain leavers, so it stays small and cheap.

Rollout and rollback

PRs merge in order 5.0 → 5.6, each small. The chat falls back to cards without a key, and BACKEND=demo keeps the mocked org, so the real systems can be switched off with one setting. Revert a squash commit to roll back code. For AWS, rollback is the destroy plan: make aws-destroy-plan, approve, make aws-down, then make aws-check prints 0. Keycloak: docker compose down -v.
